## 一、已知问题（按优先级）

### P2 · 回滚只覆盖静态状态，没覆盖"因果链"

- **现状**：删除失败时的回滚是"把对象放回去"——
  导出目录从回收站移回原位、缓存键从备份 mset 回 Redis。
- **问题**：如果一个删除动作牵连了下游（比如删导出触发了下游索引更新、
  缓存失效触发了重建任务），回滚只恢复被删对象，下游的连带变化不会撤销。
  参考教训：`rm -rf /etc/nginx` 后只恢复了配置文件，遗漏了文件变动触发的
  告警脚本事件链，恢复过程又引发新一轮中断。
- **修法**：快照里记录"这次操作会产生哪些副作用钩子"，
  回滚时按逆序执行对应的补偿动作；当前没有下游依赖，暂不构成故障。


### P1 · `qa` 首字延迟偏高（8~9 秒）

- **现象**：从发请求到第一个 token 要 8~9 秒；research 只要 5.5 秒。
- **原因**：生成前串行做了两件事——意图分类（一次 LLM 调用）+ 检索策略选择（又一次），
  之后才是嵌入与精排。research 的规划与搜索是并发的。
- **修法（任选）**：
  1. 分类与策略选择合并成一次结构化输出（省一次往返）
  2. 策略选择加缓存（同问题第二次直接命中）
  3. 简单问题跳过策略选择，默认「直接检索」
- **影响**：纯体验问题，不影响正确性。

### P2 · deep 模式对 JS 渲染页面无效

- **现象**：`fetch_page` 用 `httpx.get` 抓 HTML，对 React/Vue 之类的客户端渲染站点，
  拿回来的只是空壳骨架，正文由 JS 注入。
- **影响**：这类站点 deep 模式读不到内容，只能退回 Tavily 摘要。
- **修法（较重）**：接入无头浏览器（playwright）或换成返回已渲染正文的抓取服务；
  也可以先检测"提取出的正文过短"再提示模型换一页。

### P2 · Dockerfile 未验证完整构建

- **现状**：`Dockerfile`、`.dockerignore`、compose 的 `app` 服务都已写好，
  但完整构建没跑通（torch 轮子下载慢，中途搁置）。
- **待办**：跑一次 `docker build`，确认 `python:3.13-slim` 下 torch / onnxruntime /
  rapidocr 都能装上，再补 compose 的一键启动说明。

- **仍未解决**：「刚才说的月付是多少钱」，上一轮答案里明明写着"300 元/月"，

  最后仍是走联网 → 答"没找到贵司月付方案"。
  更准确地说：**记忆已经能进检索层了，但检索层认不出同义表达**。
- **修法（两个方向，A 先做）**：
  A. 历史兜底回答：判定"这是追问 且 上一轮答案里可能有答案"时，
     把上一轮答案直接交给生成模型，允许它基于历史回答、不强制进检索。
     便宜（10 分钟），风险是把旧答案当真理——需要标注"依据上一轮回答"。
  B. 提升同义匹配：FAQ 加别名（月付/按月/月度 → 收费），
     或降低召回阈值后用 reranker 兜。治本，但会影响全局召回精度，

### 2026-10-22 · 降级与异常体系补齐（原本只有 qa）

问题：`AgentFallbackHandler` 的降级映射里只有 `qa`，research 和 crawler 出错时
直接掉到系统兜底——用户只看到"服务暂时不可用"，没法判断是联网挂了还是抓取失败了。

补齐：

    异常类     WebSearchError / CrawlError / StorageError / ModelOutputError
    qa         知识库/模型不可用 → 明确告知，不编答案
    research   deep 失败 → **真的用 fast 再跑一遍**（不读正文，只靠搜索摘要）
               fast 也失败 → 说明是联网服务问题
    crawler    失败时带上入口 URL 与可能原因（站点不可达 / 反爬 / 需登录），不装作成功
    系统兜底   三个 Agent 各有各的话术，不再共用一句通用提示

关键是降级要"真降"而不是"只换句话"：`with_retry` 现在会把 args/kwargs 传给降级层，
research 的降级能拿着同一份 state 换个 depth 重跑。

响应里新增 `fallback_used` / `degraded` / `degrade_reason`
（retry_exhausted / deep_to_fast / agent_unavailable / system_fallback），
排查时能直接看出这次退到哪一层。

实测：
    qa        → ⚠️ 知识库检索暂时不可用…
    research  → ⚠️ 联网检索暂时不可用（可能是网络或搜索服务故障）…
    crawler   → ⚠️ 网页采集失败（https://example.com）…
    deep 失败 → 重跑时 depth=fast，返回结果来自 fast

测试 130 条（新增 14 条：每个 Agent 都有降级、deep→fast 真重跑、
crawler 带上入口、系统兜底按 Agent 区分、编排器透出 degrade_reason）

### 2026-10-22 · 爬虫 Agent（四层：编排 / 工具 / 存储 / 处理）

按分层架构实现：

    编排 Agent    LLM 只决定"跟进哪些链接"，停止条件由代码控制（页数/记录数/连续失败）
    工具层        fetch_page / extract_records / find_links / paginate，HTTP→浏览器降级
    存储层        crawl_tasks / crawl_pages / crawl_records 三张表分开
    处理 Agent    independent：清洗 → 聚合 → schema 校验 → LLM 归纳

几个关键决定：
- 停止条件放代码里（可预测、可测试），只有"哪条链接相关"交给模型
- 抽取按 表格 → 重复区块 → 列表 → 段落 降级，策略名写进任务日志
- 重复区块用 lxml 找"同 tag+class 出现 ≥3 次"的容器，
  取内部带 class 的子元素作字段——这是列表页最常见的形态
- 处理与采集分开：抓取失败要重抓，处理失败只要重跑处理

实测（quotes.toscrape.com，2 页）：
    抓取 2 页 / 5316 字 / 20 条记录 / 策略 block / 停止原因 max_pages
    记录形如 {text, author, tags, tag}
    处理 Agent 按 author 聚合（Einstein 4 条），并给出带引用编号的结论

踩坑：一开始只取"出现次数最多的容器"，撞上 span.text 这种叶子节点（只有 1 个字段）
      导致抽不出结构化记录 → 改为按次数降序逐个候选尝试，取第一个能抽出多字段的。

### 2026-10-22 · 租户级联网额度

`agents/research/quota.py`：Redis 计数键 `quota:web:{tenant}:{YYYY-MM-DD}`，每次真正发起搜索前扣一次。

- 默认 **500 次/天/租户**（`WEB_DAILY_QUOTA_PER_TENANT`，0 = 不限），先给足额度
- 超额返回新状态 `quota_exceeded`，提示语是"本租户今天的额度已用完，明天自动恢复"，
  与搜索服务方 429 的 `rate_limited` 区分开——用户能分清是谁的限制
- INCR 后若超额则 DECR 回退，保证已用数不失真（否则永远看不到恢复）
- 键保留 2 天，跨天自然过期，不需要额外清理任务
- Redis 不可用时**放行**并告警：额度组件故障不该让所有人用不了联网

`GET /api/v1/research/quota` 可查当天用量。

实测：
    联网前 {limit: 500, used: 0, remaining: 500}
    搜一次 {limit: 500, used: 1, remaining: 499}
    手动把计数写到上限 → search_status=quota_exceeded，返回额度提示语

### 2026-10-22 · 联网检索支持时间过滤

`web_search` 工具增加 `time_range`（day/week/month/year）与 `topic` 参数，
planner 在拆子问题时顺带判断要不要收窄时间窗口。

    什么是 RAG                → 不限
    本周 AI 领域有什么新闻     → week（MCP 日志确认参数已透传）

响应里透出 `time_range`，便于排查"为什么这次结果偏旧"。

**顺带发现一个真 bug**：做 ACL 改造时，`cache_write_node` 漏传了 department / role，

### 2026-10-22 · deep 模式：模型自主打开网页正文

`fetch_page` 原本是死代码。现在 `depth=deep` 时：

1. 第 1 轮用 `tool_choice="required"` **强制**调一次 `fetch_page`
   —— 实测提示语写"需要时再读"时，模型永远判断"不需要"，deep 就名不副实
2. 之后模型自主决定是否继续读，上限 `RESEARCH_MAX_PAGE_FETCHES=2`
3. 收尾不带工具再问一次，确保输出文本而不是工具调用

同时修了正文提取：先取 `<article>`/`<main>` → 从第一个 `<h1>` 开始切 → 去噪标签 → 块级标签转换行。
同一页面从「User Guide / Database / Collections…」（导航菜单）变成「HNSW 是一种基于图的索引算法…」。

```
fast  11.1s / 459 字 / 只用摘要
deep  36.5s / 641 字 / 读 2 页正文，能指出资料间的数值矛盾
```

### 2026-10-22 · 联网答案并入同一套缓存

qa 与 research 共用一个 `AnswerCache`，用命名空间区分：

```
qa:ans:v{ver}:s{scope}:{query}           知识库答案 TTL 24h
qa:ans:research:{depth}:v{ver}:...       联网答案   TTL 6h
```

- 不把缓存做成 MCP：缓存查询在热路径上，多一次往返和故障点反而抵消收益
- 只缓存成功结果（`answer_mode=web`），避免一次服务故障被缓存扩散
- depth 也进键，否则 deep 会命中 fast 的摘要答案（实测踩过）
- 实测：同一问题 11.2s → **0.02s**，加速 650 倍

### 2026-10-22 · 区分「搜失败」与「没搜到」

`SearchOutcome(status, items, detail)`，五种状态各有独立提示：

| 状态 | 用户看到 |
|---|---|
| `ok` | 正常作答 |
